招行
        背景
                这个项目面向银行客户经理、运营和机构客户部人员，目标是把原来偏“记录数据”的高校基金会平台，升级为能够帮助员工查数据、生成经营材料、识别机会和推动任务的 AI 经营助手。我从业务诊断、数据底座、Agent 策略、工具调用和溯源，到离线评测、UAT 和分行推广参与全链路推进。项目重点不是追求全自动，而是在金融边界内做到结果稳定、数字可追溯、动作可审核。在招商银行总行主导"校友基金会经营小助"——把散落在七八个模块里的机构、项目、资金、协议数据打通，设计了Agent的14个工具调用链路和三档人机协作模式，工具调用准确率从71%提到89%，AI内容采纳率从不到50%拉到70%。


校友会平台的需求来源方是哪些？

四个来源，优先级从高到低：
>
> **第一优先级，分行客户经理的作业痛点。** 他们是真正用产品的人——比如南京分行的客户经理要手动从 4 个系统里拼数据做拜访 brief，每次半小时。这个痛点最真实、最紧急，我们最先做。
>
> **第二优先级，总行机构客户部的经营目标。** 比如今年重点是提升高校基金会客户留存率，那留存相关的功能优先级自动提升。
>
> **第三优先级，试点高校的 UAT 反馈。** 南京大学和北京高校的 UAT 中，校方提出校友捐赠数据展示不够直观——我们在上线前紧急加了一版可视化。
>
> **第四优先级，产品数据 + badcase 归因。** 上线后看哪些功能没人用、哪些场景 Agent 出错率高，数据驱动迭代。
>
> **核心原则**：谁痛先做谁、高频优先、可复用优先。这和供应链产品需求管理逻辑一致——仓库管理员的痛点 > 管理层的 nice-to-have。


                        多Agent协作场景，用户query怎么路由到正确的Agent？整体架构怎么搭？工具怎么调用？


多 Agent 场景里，我不会让大模型直接随意选择 Agent，而是先经过一个统一的 Router 路由层，识别用户的任务意图、业务对象、所需数据和操作风险，再决定是进入单 Agent、固定 Workflow，还是拆成多个 Agent 串并行协作。

整体架构通常是：

用户入口 → 意图路由 → 任务规划与编排 → 专业 Agent → 工具网关 → 业务系统 → 结果校验与统一生成。

工具调用时，Agent 只负责判断“调用什么工具、传什么

多 Agent 架构的核心不是“让多个模型互相聊天”，而是通过 统一路由、受控编排、专业 Agent 分工和工具网关治理，把一个复杂业务 Query 拆成可执行、可校验、可追溯的任务链。


AI 经营助手的人机协同是什么样的模式？

> 核心设计是**三档人机协作模型**，按「操作风险 × 可逆性」划分：

> | 档位 | 适用场景 | 保险/供应链迁移 | 人机分工 |
> |------|---------|---------------|---------|
> | 🔵 自动档 | 只读查询：查项目资金、查沟通记录、查协议到期日 | 查库存、查物流轨迹 | Agent 自动执行，不经过人工 |
> | 🟡 确认档 | 生成类+发送类：生成拜访 brief、月报、喜报、发短信 | 生成补货建议、生成对账单 | Agent 生成→人工审核确认→执行 |
> | 🔴 接管档 | 合规敏感/大额：资金审批、双录、合同盖章 | 大额采购审批、赔付决策 | Agent 不碰，完全人工 |

> **具体场景**：客户经理说「帮我准备明天拜访南京大学校长的材料」→ Agent 自动档查项目资金、最近沟通记录、协议到期日 → 确认档生成拜访 brief 草稿 → 客户经理审核修改 → 点确认发送。整个过程 Agent 做了 80% 的脏活，人在最关键的「发送」节点把关。

> **和供应链的关联**：供应链 Agent 同样需要三档——查库存自动档、生成补货单确认档、大额采购接管档。


                                业务建模（场景拆解）- 结构化数据与非结构化数据
                                        先做业务场景拆解 - 数据盘点，确定需要哪些结构化和非结构化数据，再针对两类数据定义业务字段、文档元数据和工具输入输出 Schema。字段定义依赖数据分类，但两者会随着 Agent 编排和 Bad Case 迭代持续调整。

在招行项目中，我会在业务建模阶段就区分结构化和非结构化数据。结构化数据包括客户、账户、资金、项目、协议、权限和任务状态，主要通过行内业务接口精确查询；非结构化数据包括产品手册、政策制度、历史案例、拜访纪要和项目材料，主要通过RAG检索。

它们不是在意图识别时全部调用，而是Agent先识别任务和业务对象，完成参数提取与权限校验，再根据任务决定调用业务接口、知识库或两者同时调用。最后模型把结构化事实和非结构化知识合并，生成经营结论，同时保留数据来源和更新时间。

                                                                rag策略
                                                                        招行项目里的 RAG 策略，我主要从知识分层、Query 路由、混合召回、元数据过滤、Rerank 和评测闭环六个方面设计。首先做数据分流，结构化的客户、资金、项目状态走业务接口，制度、产品手册、案例和拜访纪要走知识库；检索时先根据用户意图路由到对应知识域，再做客户实体和业务术语标准化，通过机构、客户、权限、版本和生效时间等元数据缩小范围，之后采用关键词加向量的混合召回，再通过 Rerank （对召回内容再次排序，找出相关的片段）把有效制度、当前客户纪要和相关产品知识排到前面。

踩过的坑主要有旧制度误召回、相似客户串数据、Chunk 切得太碎导致材料不完整、Query 改写偏离用户原意，以及模型把历史案例当成当前客户事实。我们分别通过版本过滤、customer_id 绑定、按业务语义切片、限制 Query 改写范围和上下文类型标记解决。最后用固定场景评测集看 Hit Rate、Recall、MRR、过期和无权限召回率，并通过 Bad Case 持续回归。

RAG 中 Chunk 大小怎么确定？
Chunk 没有限定大小，核心看语义完整性和召回精度。
视频给出的场景化思路：
FAQ：约300–500字，一个问答尽量保持完整。
技术文档：约800–1200字，保留标题层级和上下文。
商品详情：按属性、规格、促销、评价等字段切分，而不是按字符数硬切。
同时需要：
语义边界切片。
适当重叠。
标题和父级上下文注入。
页码、版本、业务域等元数据。
父子 Chunk。

                                                                                                        策略
                                                                                                                子 Chunk 用来精准检索，父 Chunk 用来给大模型提供完整上下文。

父子 Chunk 是为了解决检索精准度和上下文完整性之间的矛盾。我们把完整章节作为父 Chunk，再拆成更小的子 Chunk。检索时用子 Chunk 做 Embedding 匹配，提高召回精度；命中后根据 parent_id 返回对应父 Chunk，让模型获得完整上下文。比如招行查询资金异常处理时，子 Chunk 能精准命中“需要核验哪些字段”，但最终会把完整的异常处理规则返回给模型，避免断章取义。

子 Chunk 负责找准，父 Chunk 负责讲全。

                                                                                知识库召回
                                                                                        知识库召回评测中，Hit Rate 看前 K 条里有没有至少一个正确知识；Recall 看应该召回的知识一共找回了多少；MRR 看第一个正确知识排得是否靠前。

用户提问后，系统从知识库里先检索出一批可能相关的文档或知识块，再经过重排交给大模型生成答案。在招行项目里，召回不能只看语义相似，还要结合业务领域、客户归属、机构权限、版本和生效时间。例如客户经理问基金会开户材料，系统要召回最新有效的基金会开户制度，不能召回普通企业制度、旧版本或者其他客户的材料。召回层主要看 Hit Rate@K、Recall@K 和 MRR；正确知识没找到属于召回问题，知识找对但模型答错，则属于生成问题。

比如招行一个经营分析问题需要资金、项目和跟进记录三个知识块，Top 5 找到了其中两个，第一个正确结果排第二，那么 Hit@5 是 1，Recall@5 是 2/3，RR 是 1/2。对整套评测集取平均后，就得到整体 Hit Rate、Recall 和 MRR。

Hit Rate 看有没有，Recall 看全不全，MRR 看靠不靠前。

                                                                                                        怎么优化召回准确率？
                                                                                                                招行项目里，我从六层优化 RAG 召回：先治理知识质量，再按业务语义调整 Chunk；通过客户、机构、业务域、版本和权限等元数据缩小检索范围；对用户 Query 做实体标准化和多意图拆解；使用关键词加向量的混合召回；最后通过 Rerank 和动态 Top K 提升排序质量。比如生成高校拜访 Brief 时，实时资金和项目状态走接口，制度、历史纪要和案例分别检索，避免全库混搜。优化效果通过 Recall@K、Hit Rate、MRR、过期文档和错客户召回率评测。

                                                                                知识库评测
                                                                                        分支主题
                                                                                                招行项目里的 RAG 评测，我分成知识质量、召回排序、生成质量和业务效果四层。

整体 Agent 评测集来自三家试点分行近三个月的 200 条真实和构造任务，其中筛出需要知识库的任务形成 RAG 专项子集。

我们先用固定的 200 条评测集做离线回归，由产品、算法和业务检查意图识别、RAG 召回、工具调用、参数和权限是否正确；达到内部门槛后，再由试点分行客户经理进行 UAT，验证真实业务中是否好用。评测表贯穿这两个阶段，用来记录标准结果、实际输出、评分和 Bad Case。71% 到 89%主要来自离线回归，UAT 更关注业务可用性和人工修改情况。

评测集不是简单的问答对，而是包含用户角色、客户对象、业务任务、正确文档、正确 Chunk、答案要点、有效版本和权限要求。构建时会覆盖正常、边界、异常、权限以及历史 Bad Case，并加入旧制度、其他客户纪要等难负样本。

评测时，我先看系统有没有找到正确资料、有没有把需要的资料找全、召回结果里无关内容多不多，以及正确资料是不是排在前面。然后再看模型有没有严格依据资料回答、答案是否完整、引用来源是否准确。只要出现调取错误客户资料、越权访问、使用过期制度或者编造内容，这条任务就直接判定为失败。

评测标准主要由我和业务人员定义，算法负责批量执行、指标统计和链路分析，最终 Bad Case 由产品、业务和算法共同判断。

评测场景、标准和上线门槛主要由我推动，因为这部分必须来自真实业务；算法团队负责评测工具、指标计算和检索参数优化；业务专家负责制度和答案正确性。最终 Bad Case 是我们共同归因，但我会负责把结果转成产品和优化优先级。

                                                                                                                                评测阶段是你参与多还是算法参与多？评测标准具体怎么设计？
                                                                                                                                        评测这件事，我的定位很清楚：**标准我来定，执行算法来跑，判断我们一起看。**
>
> **第一，谁参与多？**
>
> 评测标准的定义上，我参与更多。因为算法同学关注的是模型层面的指标——准确率、召回率、Perplexity。但业务场景里"好"的标准不是这几个数能回答的。比如招行的月报生成，算法可以告诉你"文本流畅度得分92%"，但分行同事不用，因为月报里的数字对不上、数据来源没标注、格式不符合行内模板——这些算法测不出来，只有我懂。
>
> 所以我负责回答"什么叫好"——定义评测维度和通过标准。算法负责回答"怎么测"——把维度翻译成可计算的指标和自动化脚本。评测执行算法来做，但Bad Case的归因和分类是我来做，因为我知道每个问题该归到哪个环节去修。
>
> **第二，评测标准的字段是怎么设计的？**
>
> 我不是从模型论文里找指标，而是从**业务流程的失败模式**反推评测维度。
>
> 拿招行项目举例。我在分行跟访了三周，把一线同事抱怨的问题全部记录下来，然后反向归类：
>
> | 一线同事的原话 | 对应的评测维度 | 评分标准 |
> |---|---|---|
> | "AI写的数据和我系统里看到的不一样" | **事实准确率** | 关键数字（金额、日期、项目数）是否与源系统一致 |
> | "它给我推了一个我根本没权限看的客户" | **合规边界** | 是否调用了用户无权访问的数据 |
> | "我就问个资金情况，它给我生成了一篇报告" | **任务完成度** | 是否按用户意图完成，不多做也不少做 |
> | "它调了五次接口都调错了" | **工具选择准确率** | 是否正确选择了工具和参数 |
> | "这个数字是哪来的？" | **数据溯源** | 每个数字能否追溯到源系统和查询时间 |
> | "格式不对，我得重新排" | **输出格式** | 是否符合月报/Brief/机会推送的标准模板 |
>
> 每条维度都有一条"一线原话→评测字段→评分规则"的对应链。这样算法同学拿到评测标准时，不只是看到"准确率"三个字，而是知道"这个准确率对应的是客户经理说的'数字对不上'这个问题"。
>
> **第三，架构和逻辑是什么？**
>
> 我的评测体系分三层，不是一次性跑完就了事：
>
> ```
> 第一层 · 样本层
> 200条固定真实场景样本，覆盖：
>   正常场景（70条）——高频查询、标准生成
>   边界场景（60条）——参数缺失、数据为空、相似实体混淆
>   异常场景（40条）——越权查询、合规红线、接口超时
>   历史Bad Case（30条）——以前出过错的场景，确保不复发
>
>        ↓
> 第二层 · 评分层
> 每条样本跑完，八个维度逐条打分（通过/不通过，非黑即白）：
>   任务完成 | 工具选择 | 参数准确 | 执行链路
>   数据溯源 | 合规边界 | 拒答合理 | 输出格式
>   最终得 = 通过的维度数 / 8
>
>        ↓
> 第三层 · 归因层
> 不通过的维度，归到四个根因之一：
>   工具层（工具描述不清晰、参数定义有歧义）→ 改工具定义
>   Prompt层（指令不明确、约束遗漏）→ 改Prompt
>   数据层（源数据缺失、接口超时）→ 改数据底座或增加兜底
>   规则层（业务逻辑本身有漏洞）→ 改业务规则
>
>        ↓
> 回归验证：改动后 200条全量重跑，20分钟出结果
> ```
>
> 比如说，Agent 有一次把"北京高校"理解成了"北京所有高校"，但客户经理只想看"北京大学"。归因到 Prompt 层——我在 System Prompt 里加了"机构名称模糊时，列出候选让用户确认，不允许自动选择"。加完后回归全量跑，这个维度的通过率从 82% 提到了 96%。
>
> 核心逻辑是：**评测不是算法的事，产品经理要定义"什么叫好"——而这个定义只能从一线业务流程的失败模式里来，不能从论文里找。**

                                                                                                        评测表和评测集
                                                                                                                评测集是“题库”，评测表是“答题卡＋成绩单”。

评测集是拿什么来考，评测表是按照什么标准判、最后得了多少分。

在招行项目中，我们先确定任务完成、工具选择、参数准确、执行顺序、数据溯源、权限合规等评测维度，并设计统一的评测表。之后再从真实业务问题、UAT 和 Bad Case 中建设约 200 条评测集。每次模型、Prompt、工具或流程调整后，都跑同一套评测集，并把结果回填到评测表中，对比优化前后的变化。

                                                                                                                                                子主题
                                                                                                                                                        讲讲你设计评测集的思路——怎么构建场景化的评测集来保证Agent效果？
                                                                                                                                                                我的评测集设计方法论叫**"场景分层+边界覆盖+固定样本回归"**。

> **第一步：场景分层。** 不是随机抽问题，而是按场景分类覆盖：
> - 高频正常场景（占80%实际用量，必须满分）：如"查XX高校的资金情况"
> - 复合意图场景（多步骤任务）：如"帮我准备拜访南大的Brief"
> - 边界场景（参数缺失/模糊）：如"帮我查一下那个项目"（没说哪个）
> - 异常场景（数据为空/接口超时）：如查一个没有任何资金记录的项目
> - 对抗场景（越权/敏感信息）：如"把XX高校的捐赠人联系方式给我"

> **第二步：定义评测维度。** 招行经营小助的8维评测体系：

> | 维度 | 测什么 | 怎么打分 |
> |------|--------|---------|
> | 任务完成 | 用户意图是否被正确执行 | 0/1 二元 |
> | 工具选择 | Agent是否选了正确的工具 | 0/1 |
> | 参数填写 | 传给工具的字段是否准确 | 0/1 |
> | 决策链合理 | 执行顺序是否符合业务逻辑 | 1-5 |
> | 数据溯源 | 每个数字能否追溯源系统 | 0/1 |
> | 合规红线 | 是否触碰不该碰的决策 | 通过/不通过 |
> | 拒答合理 | 该拒时拒了、不该拒时没误拒 | 0/1 |
> | 输出格式 | 结构是否符合模板 | 1-5 |

> **第三步：固定样本+全量回归。** 从试点分行过去3个月的真实场景中抽取200条样本，每条样本保留"原始系统数据+客户经理最终提交版本"。每次调Prompt或规则，20分钟全量重跑，8个维度的分数变化一目了然。

> **关键心法：评测集不是一次性的，是活的——每发现一个新Bad Case，就把它加入评测集，确保同类错误不会再次出现。**

                                                                                > 这个Agent的核心场景是：客户经理说一句"帮我准备明天拜访南京大学的Brief"，Agent需要自动完成四件事——查高校档案→查下面挂的项目→查每个项目的资金到位和协议状态→查最近沟通记录→生成拜访Brief。

> **Agent角色定义**：经营分析助手，不是通用聊天机器人。它的边界是"分析已有数据→生成材料→推荐动作"，绝不能"替客户经理做资金决策"。
>
> **Skill拆分**：我把Agent的能力拆成6个Skill——数据查询Skill（调14个后台接口）、全景分析Skill（整合多模块数据）、材料生成Skill（月报/Brief/喜报）、机会识别Skill（资金未到账/协议临期/项目停滞）、任务协同Skill（创建跟进提醒）、合规审核Skill（敏感信息和权限校验）。
>
> **Workflow编排**：不是线性流水线，而是有分支判断——比如查某高校时如果发现它下面有5个项目，Agent要逐个查每个项目的资金和协议状态，再汇总。判断要调用哪些 Workflow；
决定调用顺序；
根据上一步结果决定下一步；
缺少参数时追问用户；
工具失败时重试或换方案。
如果某个接口超时，要有降级策略（先返回已有数据+标注缺失项）。
>
> **工具依赖**：14个后端API，我按客户经理心智模型重组了工具描述——不是"调用资金查询接口"，而是"先查机构→再看项目→再看资金→再看协议→最后看沟通记录"。
>
> **知识依赖**：报告模板、合规话术、品牌规范、历史优秀案例。
>
> **评估指标**：8维评测——任务完成、工具选择、参数准确、决策链合理、数据溯源、合规红线、拒答合理、输出格式。
                                                                                        固定链路通常更适合 Workflow，因为调用次数、路径和输出结构可控；
开放性任务更适合 Agent，但它可能因为规划、反思和多工具调用增加成本。

我们会根据任务复杂度选择方案，并通过首轮成功率、平均调用次数、人工干预和合格结果成本进行评估。

                                                                                记忆识别
                                                                                        我认为生产级 Agent 的记忆系统不能简单等同于向量数据库加 RAG。向量检索主要解决语义相似性，但记忆系统还要解决状态管理、时间有效性、权限、更新和经验沉淀。
在架构上，我会把记忆至少分成四层。第一层是会话元数据，维护当前用户、任务和执行步骤；第二层是结构化档案卡，保存经过确认的用户属性、偏好和业务事实；第三层是近期对话摘要，用于压缩历史上下文；第四层是滑动窗口，保留最近几轮原始对话，处理省略和指代。向量库主要承载需要语义检索的长期记忆，而不是统一保存所有状态。

第二个重点是时间冲突。我会给状态型记忆增加双时间字段：业务上的有效时间和系统的记录时间。检索当前信息时，先按用户、权限和有效时间过滤，再做语义召回，避免已经失效的旧状态污染当前答案，同时保留历史记录用于审计。
第三个重点是程序性记忆。对于高频且经过验证的成功执行路径，不应该每次都让大模型重新规划，而应沉淀成 Workflow、Skill 或 SOP，包括工具顺序、参数约束、校验条件和异常处理。这样 Agent 积累的不只是“用户说过什么”，还有“这类任务应该怎样稳定完成”。
所以，完整的 Agent 记忆系统应该做到分层存储、按需召回、时间可追溯、权限可控制、信息可更新，并能够把成功经验固化为可复用能力。
                                                                                                什么信息值得写入长期记忆？

不是每句话都应该写入。写入前需要判断信息是否稳定、是否与未来任务相关、是否得到用户明确确认，以及是否涉及敏感信息。像稳定偏好、长期身份和经过验证的业务事实可以进入长期记忆；临时情绪、一次性指令和未经确认的推测通常只保留在当前会话。写入后还要支持更新、过期、删除和权限审计。

RAG 解决的是“从历史内容中找到什么”，而生产级记忆系统还必须解决“存什么、放哪里、什么时候有效、能否使用，以及如何把经验变成能力”。
                                                                                                        多轮对话中的记忆怎么分层？缓存怎么设计？
                                                                                                                记忆不是越长越好，而是越有条理越好。我会按短期上下文、会话摘要、用户档案和业务知识分层，并以 user_id、session_id、task_id 进行隔离。缓存设置 TTL、版本号和失效策略，状态型数据不能只依赖向量库。

                                                agent
                                                        我理解 Agent 并不是一个更大的模型，而是一套围绕大模型构建的任务执行系统。  
大模型本身更像一次性的推理引擎，没有天然的长期记忆。Agent 会在模型外增加 Memory、Planning、Tools 和 Execution Loop（agent执行循环：Agent 不是一次性生成答案，而是不断重复“判断下一步 → 执行动作 → 查看结果 → 再判断”，直到任务完成或触发停止条件。）。它先理解用户目标并拆解任务，然后调用搜索、数据库或业务 API，读取工具返回结果，再根据结果决定下一步，形成“规划—行动—观察—再规划”的闭环。  
Agent 的记忆也不是简单保存所有聊天记录。短期记忆主要维护当前任务状态，长期记忆保存稳定信息，RAG 则负责按需检索外部知识。工程上需要做信息筛选、摘要和状态更新，否则上下文越长，噪声和成本越高。  
当任务变复杂时，单 Agent 容易出现上下文混乱、规划失误以及缺乏独立校验的问题。因此可以引入多智能体，把规划、检索、执行和审核拆成不同角色，通过共享状态或消息协作。但多 Agent 会增加通信成本、时延和错误传播，所以是否拆分，应该取决于任务是否真的需要专业分工和独立验证。  
所以我认为，评价一个 Agent 系统不能只看最终回答像不像人，而要看任务完成率、工具调用准确率、过程可追溯性、异常恢复能力，以及成本和时延。
                                                                我认为 Agent“能跑通”和“能落地”是两件完全不同的事情。能跑通通常只是把大模型和几个 API 串起来，证明某条理想路径可以执行；但真实业务里存在模糊需求、参数缺失、工具异常和权限限制，如果没有工程化控制，Agent 很容易在某个中间环节出错，并把错误一直传递到最终答案。
我通常从三层解决这个问题。
第一层是需求结构化。先把自然语言转换成明确的任务 Schema，定义用户目标、实体参数、必填字段、业务约束、输出格式和完成标准。缺参数时不能让模型猜，而要触发追问。
第二层是链路原子化。把复杂任务拆成多个输入输出明确的步骤，例如意图识别、参数校验、工具调用、结果校验和内容生成。每一步都设置成功条件、异常处理和重试策略。这样不仅能提升稳定性，出现 Bad Case 时也能快速定位根因。
第三层是建立反馈闭环。保留完整执行 Trace，不能只评最终文案，还要评意图识别、工具选择、参数准确率、任务完成率、异常恢复能力和业务采纳率。线上失败案例经过归因后进入固定评测集，每次版本变更都做回归测试。
所以，一个可落地的 Agent 不是“大模型加几个 API”，而是一套包含需求建模、流程编排、状态管理、异常处理和评测监控的任务执行系统。

我不会用“成功演示一次”判断，而会至少看四类指标：
第一是任务完成率；第二是工具选择和参数准确率；第三是异常场景下的恢复或合理拒答能力；第四是业务指标，例如采纳率、人工修改率、处理时长和单位任务成本。
同时还要按正常、边界、异常和历史 Bad Case 分层构建评测集，否则平均准确率可能掩盖真正的上线风险。

Agent 落地的关键不是继续调 Prompt，而是把不可控的模型能力，放进可拆解、可校验、可观测、可回归的工程系统里。
                                                                        生产级 AI Agent 系统架构怎么设计？
                                                                                我会按入口、编排、模型、工具、记忆和基础设施六层设计。请求经过鉴权和意图识别后，由 Planner 拆解任务，Executor 调用模型或工具，状态存入工作记忆；长任务通过状态机和消息队列执行，最终由结果聚合模块生成可追溯答案。
                                                                        Agent 的规划、执行、反思闭环怎么实现？
                                                                                我会用显式状态机实现 Plan—Act—Observe—Reflect 闭环。Planner 输出结构化执行计划，Executor 逐步调用工具，Reflector 根据结果、业务规则和完成标准决定继续、重试、改计划还是终止。必须设置最大步数、重试次数和人工确认节点，防止死循环。
                                                                        高并发下 Agent 服务怎么做弹性伸缩？
                                                                                高并发下我会把编排执行层设计成无状态 Worker，把会话和任务状态外置到 Redis 或数据库，通过消息队列削峰。扩缩容不能只看 CPU，还要结合队列积压、活跃任务数、P95 延迟和模型限额。对长任务保存 Checkpoint，保证实例重启后能够继续执行。
                                                                        多个串行工具导致延迟高，怎么优化？
                                                                                我会先通过 Trace 拆解每个节点的 P50、P95 和错误率，找到尾延迟最高的步骤。对无依赖调用并行化，对稳定结果缓存，对简单判断使用小模型或规则，并设置超时降级。用户体验通常由最慢的 P95 环节决定，而不是平均值。
                                                                        工具 Description 怎么写，模型才能准确调用？
                                                                                工具描述要解决用途、边界、输入约束和负样本四件事。很多工具误调用并不是模型能力问题，而是工具职责重叠、描述含糊。
                                                        agent意图识别
                                                                
                                                                意图识别
                                                                        在意图识别设计上，我不会把所有请求直接交给大模型，而会采用三层漏斗架构。

第一层是规则层，用关键词、正则和有限状态机处理高频、明确、表达固定的意图，例如查询、取消和转人工。这一层延迟最低、结果最稳定，但要控制规则数量，避免维护成本失控。
第二层是上下文层，用轻量分类模型、Embedding 匹配（Embedding 匹配，就是把用户 Query 和 Agent 能力描述都转换成向量，再计算它们的语义相似度。Embedding 匹配就是把用户 Query 和每个 Agent 的能力描述向量化，通过语义相似度召回最相关的 Agent。它适合做候选 Agent 的初筛，但不能单独作为最终路由，还要结合权限规则、置信度和大模型二次判断。）和对话状态管理处理大多数已知业务意图。它不只判断当前句子，还要结合上一轮意图，理解省略和指代。例如用户先问南京大学的项目进度，下一句只说“那复旦呢”，系统要继承查询项目进度这个意图，只替换机构参数。
第三层才是大模型兜底。对于多意图组合、表达模糊或者前两层置信度不足的请求，让大模型完成任务拆解、工具选择和参数生成。如果大模型仍然无法确定，就触发澄清问题，而不是直接猜测。

这种设计的本质是让低成本、确定性高的方案处理多数已知问题，让大模型只解决少数真正需要语义推理的长尾问题，从而兼顾准确率、响应速度、吞吐量和推理成本。
                                                                                你怎么评估意图识别？

我会按意图分别看 Precision、Recall 和 F1，而不是只看整体准确率，因为高频意图可能掩盖长尾意图的问题。同时评估规则命中率、轻量模型承接率、大模型兜底率、低置信度追问率、误路由率、平均响应时间和单次请求成本。对于高风险业务，误路由的代价高于多问一次，因此置信度阈值会设置得更严格。

好的意图识别不是让大模型理解所有请求，而是用分层路由把确定性问题挡在前面，把大模型留给真正复杂的长尾问题。
                                                                        路由
                                                                                意图识别可以由 Agent 做，但我不会把所有意图识别都设计成一个复杂 Agent。简单明确的请求，可以通过规则和大模型分类器完成；涉及多意图、上下文依赖、任务拆解和二次转交时，再由 Router Agent 完成。

在项目建设顺序上，我不会先做 Agent，而是先拆业务场景，然后梳理结构化数据、知识库和业务工具，再把可复用的单项能力封装成 Skill，把多个 Skill 按稳定业务顺序编排成 Workflow，最后由 Agent 负责识别意图、选择能力和动态调度。

例如招行的资金趋势分析是 Skill，拜访材料生成是 Workflow，Router Agent 则负责判断用户是只想看资金变化，还是需要启动完整的拜访准备流程。

星辰维度里，画像提取、课程推荐和卡点诊断是 Skill，学习规划和内容生产是 Workflow，Agent 负责根据用户当前问题选择对应能力。


建设顺序是场景、底座、Skill、Workflow、Agent；运行顺序是 Agent 识别意图，再调 Workflow、Skill、知识库和工具。

                                                                        上下文管理
                                                                                我理解 Agent 的上下文管理，不是简单保存全部历史对话，而是在有限 Token 预算内动态组装当前任务所需的信息。
我通常把上下文分成五类：

第一类是系统指令和安全边界；
第二类是当前任务、意图和参数；
第三类是近期对话滑动窗口；
第四类是任务状态和经过筛选的工具结果；
第五类是按需召回的长期记忆和 RAG 证据。

在信息优先级上，当前目标、用户约束、已确认事实和任务状态必须优先保留；寒暄、重复内容、过期状态和冗长工具日志可以裁剪。对于较早的对话，我不会生成一段模糊的自然语言摘要，而会压缩成结构化状态，包括目标、约束、已完成步骤、待办、关键决策和未解决问题。
当上下文接近预算阈值时，会先去重和裁剪工具结果，再压缩早期对话，同时保留最近几轮原文。如果任务非常长，就将关键状态写入外部存储并创建 Checkpoint，再启动新的上下文窗口。长期知识和用户记忆则根据当前意图按需召回，并进行权限、时效和相关性过滤。
所以我认为，生产级上下文管理的本质不是扩大窗口，而是做好信息分层、优先级排序、状态外置、动态压缩和按需召回。
                                                                                        如何避免摘要压缩丢失关键信息？

我会同时采用结构化摘要和原始事件留存。摘要中强制保留目标、约束、事实、决策、待办和证据引用，并给关键字段设置不可丢弃优先级；原始对话和工具结果保存在外部日志中，摘要只作为运行时视图。这样即使摘要出现信息损失，也可以通过引用 ID 回查原始记录。另外会使用固定样本评估压缩前后的任务完成率和关键事实保留率。

上下文管理不是“记得越多越好”，而是让模型在正确的时间，只看到完成当前任务所必需的正确信息。
                                                                不是一到意图识别就把所有数据调出来，而是先识别任务，再按任务需要调用对应的数据。

在同一套 200 条回归样本中，优化前完整通过 142 条，任务级准确率是 71%；优化工具描述、参数校验、Workflow 前置条件和 Prompt 后，通过 178 条，提升到 89%。

                                                skill、workflow
                                                        Skill 是 Agent 掌握的一项可复用业务能力，Workflow 是把多个 Skill、工具和规则按照业务顺序编排成完整任务。

在招行项目里，客户画像、资金趋势分析、机会识别、经营材料生成都可以封装成 Skill；而“生成客户拜访材料”“识别经营机会并创建跟进任务”属于 Workflow。
在星辰维度里，用户画像提取、课程匹配、选题生成、脚本生成是 Skill；从画像到知识召回、内容生成、质量检查再到复盘，就是 Workflow。

以招商银行的客户拜访准备为例，查询客户信息、账户余额和历史流水属于 Tool；把多个数据组合起来判断资金变化，属于资金趋势分析 Skill；把客户画像、资金变化、历史跟进、产品资料和经营机会串起来，最终生成拜访材料，就是完整的 Workflow。

星辰维度也是一样，用户画像提取、课程匹配、选题生成、脚本生成都是可复用 Skill；而从采集画像、召回知识、生成选题、生成脚本、质量检查到输出发布素材，是一个内容生产 Workflow。

所以我会把 Skill 理解为可复用的能力模块，把 Workflow 理解为完成业务目标的流程编排，而 Agent 负责根据用户目标决定调用哪个 Workflow 和哪些 Skill。

                                                prompt
                                                        Prompt 不只存在于 Agent 里，它会分布在 Router、Skill、Workflow 的各个模型节点中。

Agent 决定做什么，Workflow 规定先后顺序，Skill 封装具体能力，Prompt 告诉模型在当前节点应该怎么判断、怎么生成。

我们先定义业务任务和能力边界，用 Prompt 快速验证模型可行性；确认有效后，再补充知识库、业务工具、结构化输入输出和校验规则，把单项能力沉淀成 Skill，再通过 Workflow 编排，最后由 Agent 做动态路由和决策。

Prompt 不只放在 Agent 里，而是分布在路由、Skill 和 Workflow 的各个模型节点中。Router Prompt 用来识别意图和抽取参数，Agent Prompt 定义目标拆解、能力选择和执行边界，Skill Prompt 负责完成具体业务能力，Workflow 中的分析、生成和校验节点也都有各自的 Prompt。

例如招行的经营机会识别 Skill，会通过 Prompt 规定机会类型、判断依据和输出格式，但客户资金数据必须由 Tool 查询，制度内容来自知识库，权限由后端校验。星辰维度里，画像提取、课程推荐、选题生成和卡点诊断，也都有独立 Prompt，再被编排进学习规划或内容生产 Workflow。

所以 Prompt 是模型节点的执行指令，不是整个系统架构，也不能替代知识库、工具、Workflow 和权限规则。

Prompt 负责告诉模型“这一步怎么想、怎么输出”，Workflow 负责“步骤怎么走”，Skill 负责“能力怎么复用”，Agent 负责“现在该调用谁”。

                                工具调用
                                        我在这一块主要参与的是整体业务架构和产品方案设计，包括意图体系、Agent能力边界、工具清单、工具与业务意图的映射、输入输出Schema、必填参数、缺参追问、权限规则、异常处理以及UAT验收标准。底层工具网关、接口服务和数据库代码由后端及架构团队实现，但我会参与接口评审、联调、权限验证和Bad Case复盘。

                                                                                                                > 我们的工具调用准确率采用的是严格的任务级口径。在 200 条脱敏后的真实业务样本中，只有工具选择、参数、调用顺序、结果使用和权限判断全部正确，这条任务才算通过。
>
> 优化前有 142 条完整通过，所以是 71%；优化后同一批样本有 178 条通过，所以提升到 89%。对于一条任务调用多个工具的情况，主指标按整条调用链计算，只要关键步骤错一个，任务就判失败；内部还会看步骤级准确率，用来定位具体是哪一个工具或参数出了问题。
>
> 样本来自三家试点分行过去三个月的月报、拜访 Brief 和经营机会推送等真实场景。业务人员负责确认标准业务结果，产品和测试按照统一评分表检查工具、参数和执行链，争议样本再由业务、算法和后端共同复核。
>
> 这次提升主要不是简单改 Prompt，而是系统性优化了工具描述和路由规则、参数 Schema 和调用前校验，把稳定链路从自由 Agent 调度改成 Workflow，同时增加了上下文状态管理、异常重试、权限校验和 Bad Case 回归，所以工具选择、参数缺失和调用顺序错误明显减少。

                                        工具是MCP还是什么形式？固定流程还是自主调用？
                                                > 工具形式上是把14个行内后端API封装成标准化的Function Call工具，不是MCP协议。两者属于不同层级，Function Call 负责表达调用意图，MCP 负责统一连接和提供工具。并且每个工具有名称、描述、参数schema、返回格式、权限要求。

MCP 是连接 Agent 与工具、资源、Prompt 的标准协议，不是某一个具体业务工具。



> 调用模式分两类：**只读工具**（查机构/查资金/查项目进度）允许Agent自主组合调用顺序；**写入工具**（创建任务/发起审批/发短信）必须走固定Workflow+人工确认节点。判断标准是风险等级——读操作可自主、写操作要审批。

                                                        招行项目里的 Function Call、MCP、Skill 和工具调用处于不同层级。

早期 PoC 阶段，我们先通过 Function Call 让模型能够选择资金查询、客户查询等工具并生成结构化参数。进入试点后，在模型和行内接口之间增加工具网关，负责参数校验、权限鉴权、敏感操作确认和审计日志。随着接入系统增多，可以通过 MCP 将客户、账户、项目和知识库能力统一暴露给 Agent，降低模型与业务系统的耦合。再往上，我们把多个原子工具封装成经营分析、机会识别、拜访准备等 Skill，由 Workflow 或多 Agent 负责编排。最终形成的是从意图识别、Skill 选择、Function Call、MCP 连接、权限校验到真实工具执行的完整闭环。

                                                                                                MCP（Model Context Protocol）是Anthropic提出的Agent与外部工具/数据源之间的标准化连接协议。核心理念是：**让Agent像USB一样即插即用地连接各种工具和数据源，而不是每个Agent都要单独做工具对接。**

> **在蚁小保的应用设计**：
>
> **短期落地**：
> - 把保单查询、保费试算、理赔报案等核心工具封装为MCP Server
> - 好处：不同Agent（选购Agent、理赔Agent、客服Agent）共享同一套工具协议，避免重复开发
> - 工具变更时只改Server端，所有Agent自动适配
>
> **中期扩展**：
> - 引入外部MCP Server：医院网络查询、药品目录查询、监管政策实时更新
> - Agent可以动态发现新工具——比如监管发布新规定，MCP Server更新后Agent自动可用
>
> **设计关键**：
> - MCP不是万能解药——保险场景的工具权限比工具连接更重要
> - 每个MCP Server需要有独立的权限管控：理赔Agent能调用「提交报案」MCP Server，产品对比Agent只能调用「保单查询」只读接口
>
> **我的判断**：MCP是Agent生态的基础设施，但不是产品经理的核心KPI。产品经理的核心工作是设计「Agent什么时候用什么工具、按什么顺序、怎么兜底」——MCP解决的是「连得上」的问题，产品解决的是「用得对」的问题。

                                                                        参数校验
                                                                                参数校验（结构校验）不是简单放在意图识别之前或之后，而是分层做。意图识别前只能做输入安全和身份等基础校验；识别出意图后，才能根据任务提取参数、判断缺参并进行槽位补全；模型生成 Function Call 后，再由工具网关按照 Schema 校验参数格式；真正进入业务接口前，还要做客户真实性、数据权限、时间范围和业务规则的强校验。所以核心业务参数校验是在意图识别之后、工具实际执行之前完成的。

                                        难点：意图识别→工具调用→权限隔离，你怎么定义这些规则？
                                                在招行项目里，我把规则定义成三层。

**第一层是意图规则。**先定义客户经理有哪些高频任务，比如客户查询、资金分析、机会识别、材料生成，再明确每类意图对应的业务对象、必填参数和可进入的流程。

**第二层是工具规则。**每个意图只能调用指定工具，并定义工具的适用场景、参数来源和执行顺序。比如资金分析必须先确认客户ID，再查询账户和资金数据，不能跳过前置步骤，也不能由模型编造参数。

**第三层是权限规则。**根据用户角色、所属机构、客户归属、数据范围和操作类型，动态决定他能看到哪些工具、能查询哪些数据。即使模型选对工具，执行前后端仍会再次鉴权；涉及创建、修改和外发的操作，还要人工确认。

核心原则是：**意图决定走哪条业务链，工具规则决定怎么执行，权限规则决定能不能执行。**

                                Bad Case回归具体怎么做的？
                                        Bad Case 在知识建设、离线评测、UAT 和上线后都会产生，但最重要的归因节点是离线回归评测。因为这个阶段有固定样本、标准答案和完整执行链路，可以明确判断问题是出在意图、知识、检索、工具、权限还是生成层。UAT 更关注真实业务是否好用，上线后则关注新问题和风险问题；这两个阶段发现的 Bad Case，最终也会回流到离线评测集里做修复和回归。

Bad Case 在需求设计、知识建设、联调、离线评测、UAT 和上线后都会出现，但最重要的正式归因节点是离线回归阶段。因为这个阶段有固定样本、标准答案和完整 Trace，可以系统判断问题出在意图、知识、检索、工具、权限还是生成层。UAT 主要补充业务可用性问题，线上监控发现未覆盖的新问题，最终都要回流到固定评测集，形成发现、归因、修复、回归和防复发的闭环。

                                        案例
                                                先拆任务，再校验客户和权限；实时事实查接口，制度和纪要走 RAG；出现错误先看 Trace 定位层级，修复后用原样本回归，最后再由业务用户做 UAT。
                                                        招行项目里，我用“生成高校基金会项目的拜访 Brief”举例说明整个 Agent 流程和 Bad Case 归因。

客户经理输入：“帮我准备明天拜访南京大学基金会项目的 Brief，重点看开户材料、当前进度和上次沟通的待办。”

第一步是意图识别和任务拆解。系统要识别这不是一个简单问答，而是一个材料生成任务，并拆成三个子任务：查询项目当前进度、检索最新基金会开户制度、查询该客户最近的拜访纪要。

第二步是实体和权限校验。系统把“南京大学”映射成标准 customer_id，再根据当前客户经理的所属分行、客户归属和数据权限，判断他是否有权查询这个客户。这里不能让模型自己猜客户编号，也不能先召回资料再做权限判断。

第三步是数据获取。项目进度、协议状态和待办事项属于实时结构化数据，通过业务接口查询；开户材料和业务规定通过 RAG 检索最新有效制度；上次沟通内容则按 customer_id 和时间范围检索该客户的拜访纪要。

第四步是 RAG 召回。系统先按基金会业务域、制度类型、有效版本和用户权限过滤，再通过关键词加向量的混合检索召回候选内容，经过 Rerank 后，把正确制度和当前客户纪要交给模型。最后模型按照固定 Brief 模板生成客户背景、项目进度、开户材料、历史待办、风险和下一步建议，并标明信息来源。

这个场景在离线回归中出现过一个典型 Bad Case：最终 Brief 引用了旧版开户制度，而且漏掉了一项授权材料。

我们没有直接改 Prompt，而是顺着 Trace 逐层排查。先确认意图和工具调用都正确；再看知识库，发现新版制度已经入库；继续看召回结果，发现新旧版本都被召回，但旧版因为关键词匹配更高排在前面，同时材料清单被切得太碎，部分 Chunk 没有进入最终 Top K。

所以根因不是模型不会回答，而是版本过滤和 Chunk 策略有问题。我们给文档补充生效日期、失效日期和有效状态，检索前过滤旧版本；材料清单改为整体保留，并使用父子 Chunk补充上下文；同时把这个案例加入固定回归集。

修复后重新跑同一条样本，正确制度进入前几位，材料清单召回完整，Brief 通过离线回归。之后在 UAT 中，客户经理反馈内容虽然准确，但篇幅太长、行动项不突出，我们又调整了输出模板，把“本次拜访重点”和“下一步待办”放到前面。

所以这个案例体现了完整闭环：业务场景设计、意图拆解、权限校验、结构化接口、RAG 检索、内容生成、离线归因、修复回归和 UAT 验收。离线回归最适合定位技术链路问题，UAT主要验证真实业务是否好用。

                                        总结，难点：我在 RAG 优化里面不会只看最终回答，而是建立完整 Trace 链路，从 Query理解、召回、排序、生成四层定位 Bad Case。比如招商银行经营助手里面，如果客户经理查询高校资金机会，但模型回答不准确，我会先看正确资金报告有没有进入召回结果，如果没有就是 Recall 或知识治理问题；如果召回正确但回答编造数据，就是 Prompt 或 Grounding问题。星辰维度也是类似，我们通过知识库分层、Chunk优化、评测集建设，把工具调用和内容生成质量持续提升。

                                                        你怎么定位AI失效的问题——模型/Prompt/知识/检索/流程，你怎么判断是哪一层的问题？
                                                                我一般用“分层排查法”定位 AI 失效问题。

先看流程有没有走错，比如任务拆解、工具顺序是否正确；再看检索结果，确认正确资料有没有被召回；如果没召回，就继续判断是知识库缺失，还是 Chunk、Query 或排序策略有问题；如果资料已经正确进入上下文，但答案仍然错误，再判断是 Prompt 约束不足，还是模型本身理解和推理能力不够。

简单来说就是：**先看流程，再看检索和知识，最后看 Prompt 和模型。**我不会一看到答案错误就直接改 Prompt，而是先通过 Trace 找到真正出错的节点。

                                                                        比如用户问“基金会开户需要哪些材料”，Agent 最后漏答了一项。

我会先看流程有没有正确进入 RAG；流程没问题，再看检索结果里有没有召回完整材料。如果正确材料根本没进上下文，就是知识缺失、Chunk 切分或召回问题；如果材料已经完整召回，但模型还是漏答，才继续排查 Prompt 是否要求完整列举，或者模型是否稳定。

所以我的判断逻辑是：**先看链路有没有走对，再看资料有没有找对，最后才看 Prompt 和模型。**

                                                        你怎么推动Bad Case的归因→修复→验证闭环？
                                                                我推动 Bad Case 闭环一般分四步：先通过 Trace 定位问题层级，再拉产品、算法和研发确认根因；然后明确修复方案、负责人和版本；修复后用原样本做离线回归，确认通过后再加入固定评测集，防止后续版本复发。

比如基金会开户问题召回了旧制度。我们排查后发现不是模型问题，而是旧文档没有失效标签。于是补充有效期字段，并在检索前过滤旧版本；修复后用同一条样本重新测试，确认只召回最新制度，再把这条 Bad Case 长期保留在回归集中。
                                整体架构
                                        招行经营助手整体可以分成入口层、路由编排层、Agent能力层、知识与数据层、工具网关层、业务系统层，以及贯穿全链路的权限、审计和评测体系。用户 Query 先经过身份和上下文补全，再由路由层识别意图、业务对象和所需工具；Agent 不直接访问数据库，而是通过工具网关生成结构化参数，经过参数、权限和风险校验后调用行内接口，最后把多个工具结果汇总成经营分析或行动建议。

                        设计巧思与产品取舍
                                溯源不是附加功能：所有经营数字需要回到源系统、字段和时间口径，用户能够快速核验。

先建议、后执行：AI 可以生成月报草稿、拜访建议和机会线索，但对外发布、客户动作和关键审批由人确认。

工具调用可观察：记录 Agent 选择了什么工具、用了什么参数、按什么顺序执行，便于复盘而不是只看最终答案。

机会必须闭环：推送不是终点，要进入认领、跟进、复核和关闭状态，才能形成经营过程留痕。

配置化而非复制粘贴：将分行差异收敛为字段映射、规则阈值、模板和权限配置，支持多机构复用。
                
                        每次修改 Prompt、工具策略或数据口径后，都用同一批 200 条真实样本做全量回归，把 AI 结果与原始数据和人工最终版本并排比较。线上再通过分行 UAT 检查业务可用性。只有整体指标提升、关键风险项没有退化，才能进入下一阶段。通过这套机制，工具调用准确率从 71% 提升到 89%，人工修改率控制在 30% 以内，验证周期从约 2 周缩短到 3 天。
        团队管理与推进
                核心协作团队约 7 人，包括后端、前端、算法和设计，并引入 2 名分行骨干做需求对接与 UAT。我的推进重点是：

把目标拆成数据底座、工具、Agent、前端体验、评测和分行推广工作包，明确责任人与依赖。

需求评审时同时确认业务价值、数据可得性、权限、异常场景和验收指标，减少开发后返工。

用固定样本和 Bad Case 作为跨产品、算法和业务的共同语言，避免“感觉变好了”的争论。

分行推广不只交付功能，还交付配置、操作说明、UAT 样例和问题闭环机制。
                        
        方法论沉淀
                这段经历让我建立了客户项目交付的基本方法：先理解甲方为什么做，再梳理用户在什么场景下使用；把模糊想法转成角色、流程、功能、字段、状态和版本计划；通过价值、频率和成本控制范围；最后用评审、跟进、测试、验收和上线数据闭环。它也让我从“把页面做好”升级为“对业务目标和最终交付负责”。
        模型选取
                招行项目的模型选型，不是选一个最强模型承担全部任务，而是根据任务复杂度、响应速度、部署合规和成本做分层。

2025年3月项目早期，我们主要处于场景验证和技术选型阶段。当时会重点评测DeepSeek-V3一类通用模型，主要看中文金融语义理解、制度问答、材料总结和结构化输出能力；对于复杂经营分析和多步骤推理，会把DeepSeek-R1作为推理模型候选。但R1响应时间更长，所以不会用于所有请求，而是只路由到资金异常分析、复杂经营建议这类高难度任务。

到了2025年4月至7月，Qwen3、DeepSeek-R1更新版本和Kimi K2陆续出现后，我们会重新做横向评测。评测不只看通用榜单，而是用招行自己的场景化评测集，重点测试意图识别、客户实体提取、工具选择、JSON参数准确率、RAG忠实度、中文金融表达、响应时间和私有化部署能力。

最终架构上，我更倾向于模型分层。简单的意图分类、Query改写和参数提取，使用轻量、低延迟的国产模型；制度问答、拜访Brief和月报生成，使用通用生成模型；需要多步骤分析的经营机会识别，再调用推理能力更强的模型。这样可以避免所有任务都调用大模型，降低延迟和算力成本。

RAG链路还会单独使用Embedding模型和Reranker。Embedding负责把用户问题和知识Chunk转成向量，做初步召回；Reranker再对候选知识重新排序。也就是说，召回模型、排序模型和最终生成模型不是同一个模型。我们可以采用BGE-M3一类中文和多语言Embedding模型，配合轻量Reranker进行私有化部署。

另外，文档进入知识库前还有OCR和版面解析能力；权限、敏感信息和高风险操作则以规则引擎和小分类模型为主，不能完全依赖生成模型判断。评测阶段也会使用独立模型做初步打分，但金融制度是否适用、客户数据是否正确，最终仍由业务人员复核。

到了2026年，DeepSeek V4、Kimi K2.6、Kimi K3和GPT-5.6可以进入新的候选池，但我不会直接替换生产模型，而是先用同一套离线评测集做A/B测试，再评估准确率、工具调用、延迟、成本和合规。国外闭源模型可以用于脱敏环境下的能力对标，但涉及真实客户数据的生产链路，优先考虑行内接入或可私有化部署的国产模型。

所以我的模型选型原则可以概括为：简单任务用小模型，复杂任务用强模型；检索、排序和生成分别选型；生产模型优先考虑安全合规和稳定性，而不是单纯追求排行榜最高。

                        早期重点评测 DeepSeek-V3 和 R1，2025 年中期把 Qwen3、Kimi K2 纳入横向评测；RAG 侧单独使用 Embedding 和 Reranker；2026 年的新模型主要作为升级候选，不会未经回归测试直接替换生产模型。
        最大难点
                招行项目中最大的难点，不是模型能不能生成一段话，而是怎样让Agent在复杂权限下，稳定地把用户问题转换成正确的业务执行链。

例如客户经理说：“帮我准备南京大学基金会项目明天的拜访Brief，重点看资金变化、开户材料和上次沟通的待办。”

这句话同时涉及三个任务：资金变化要查结构化业务系统，开户材料要检索最新制度，上次沟通要检索当前客户的拜访纪要；而且每次查询之前，还要校验当前客户经理是否有权查看这个客户。

早期容易出现的问题是，模型意图识别对了，但可能漏调工具、传错客户ID、召回旧制度，或者把其他高校的案例当成当前客户事实。它不是单纯调一个Prompt就能解决的。

我的解决方式是把链路拆成四层：第一层定义意图、业务对象和必填参数；第二层给每个任务绑定允许调用的工具和执行顺序；第三层在工具执行和RAG检索前做角色、机构、客户归属和数据范围校验；第四层通过固定评测集和Trace，对错误进行分层归因。

比如曾经出现开户材料引用旧制度的问题。我们通过Trace发现不是模型理解错误，而是新旧文档同时被召回，旧版又排得更靠前。最后通过补充生效时间和失效状态、检索前过滤旧版本、调整Chunk和Rerank策略解决，再用原样本做离线回归，并加入固定评测集防止复发。

所以我认为这个项目最大的难点，是在准确率、业务复杂度和金融合规之间取得平衡，把大模型的不确定性约束成一个可追踪、可校验、可回归的业务流程。

                        最大的难点，是让 Agent 不只是“回答得像”，而是在权限正确、数据正确和流程正确的前提下完成真实业务任务。
